Quick start

Requires Node.js 20+. Torrentor is a plain Electron app — no service, no account, no telemetry.

git clone https://github.com/sargeraas84/torrentor.git && cd torrentor
npm install
npm start

Adding sources

Every engine lives in indexers/. The registry (indexers/registry.js) is the allowlist — the app never loads search plugins from the network, and no engine can bypass the proxy-aware network client.

An adapter is one file. The contract: search(query, ctx) returns normalized results, where ctx.network is the proxy-bound client:

// indexers/my-source.js
const { normalizeResult } = require('./base');
const ENGINE = { id: 'my-source', name: 'My Source', tagline: '…', kind: 'community' };

async function search(query, ctx) {
  const data = await ctx.network.getJson(
    'https://my-index.example/api?q=' + encodeURIComponent(query),
    { timeoutMs: ctx.timeoutMs, signal: ctx.signal }
  );
  return data.items.map((it) =>
    normalizeResult({
      itemId: it.id, title: it.name, infohash: it.infoHash,
      sizeBytes: it.size, seeders: it.seeders, pageUrl: it.url,
    }, ENGINE)
  );
}
module.exports = { engine: ENGINE, search };

Then register it in indexers/registry.js. If the source is real and probe-able, add a known-good probe term so the engine-health self-test covers it.

You own the decision. Review the source's terms, rate limits and content policy before adding it. Torrentor ships legal-friendly sources by default; adding an index is a deliberate operator choice.

VPN & proxy config

Torrentor doesn't bundle or sell a VPN. It makes any VPN you already run enforceable for search traffic: every outbound engine request goes through your route, and the exit-IP check is the source of truth.

Supported proxy types

TypeUse for
socks5Recommended — Tor, ssh -D 1080, WireGuard/OpenVPN apps exposing a local SOCKS port.
socks4Legacy SOCKS proxies.
httpHTTP CONNECT proxies; credentials supported.
  1. Run your VPN

    Any client that exposes a local proxy port — Tailscale, OpenVPN, Tor Browser, ssh -D.

  2. Save & check IP

    Settings → VPN & privacy → enter host/port → Save & check IP. The app shows the exit address the world sees.

  3. Verify

    If the exit IP matches your VPN's country/city, the route is live for all engines.

Honest limits. The proxy covers Torrentor's search traffic only — file downloads happen in your torrent client and follow its settings. The app can't detect your VPN by itself; only the exit-IP check proves it.

Engine health

Settings → Search sources runs a self-test: each real engine executes a known-good probe query through the same proxy-bound path a real search uses. Healthy means the probe returned ≥ 1 result — zero results is reported as failing, never as a silent green chip.

Verdicts (ok/count/latency/error) persist locally, so dots paint instantly on revisit. Health is informational: a failing source isn't auto-disabled — you can see it's dead before enabling it.

Releasing

The release path is scripted end-to-end; these steps keep it repeatable and boring.

  1. Green master first. Push the changes and wait for the ci workflow (actionlint over every workflow + the full pure-Node suite) to pass. A red ci run means: don't tag — workflow mistakes are exactly what would break the release build.
  2. Bump + changelog. Raise version in package.json, add the changelog entry, commit, push, and again wait for ci to go green.
  3. Tag and push. git tag vX.Y.Z && git push origin vX.Y.Z — the release workflow builds Windows (installer + portable .exe) and macOS (universal .dmg + .zip), then opens a draft release with all four archives attached.
  4. Check the draft. All four artifacts present, none of the unpacked app dirs.
  5. Smoke it. Download an installer and confirm fresh-install behavior — opt-in sources (The Pirate Bay) stay off until the user enables them.
  6. Publish the draft from the Releases page when ready. That's the whole process — the download badge updates itself.

Changelog

What changed, release by release. Full notes always live on GitHub Releases ↗.

v1.4.8 — Window forcing, applied-plan provenance, clickable overlap warning

2026-09-06

  • “Apply this schedule now”. A schedule-only plan's row in the tray popover gains a Start-now button that forces its window on for this session regardless of the clock — a per-plan sibling of the night-pill override, so a 23:00–07:00 “night” plan can be exercised (or suppressed) at noon. Clicking again stops the window; a plain Apply returns it to clock-following. The force is session-only and never persisted.
  • The applied plan says where it came from. The popover notes when the armed plan was applied (“applied 11:52”) or that a relaunch restored it at boot with its last apply time — so a plan that's throttling right now is never mistaken for a fresh choice.
  • The overlap warning opens the fix. When the applied plan's window and night mode overlap at different caps, clicking the tray's warning row jumps straight into the what-if popover pre-selected — the two caps can be reconciled (switch plan, clear it, tweak limits) without hunting for the popover. Also in this release: one-click weekday presets (Weekdays / Weekends / Every day) next to the manual day toggles in both schedule editors, and a two-boot proof that the night-pill session override does not survive a relaunch (boot #2 follows the clock window again).
  • Verified end-to-end. The two-boot suite asserts the armed plan returns marked as a boot restore with its boot-#1 apply time and the override resets; the playtest forces a dormant plan's window on and off, reads the provenance note, clicks the overlap warning into the pre-selected what-if popover, and applies the weekday presets (91 pure-Node checks, 8 Electron IPC, 9 two-boot, 76 playtest steps). The real-window suite is also more robust: polled checks retry past transient DOM swaps, and keyed tray rows keep the popover's what-if state stable across re-renders.

v1.4.7 — Weekday windows, one-click night override, cap breakdowns

2026-09-05

  • Weekday-restricted windows. Both kinds of clock window — a queue plan's active-window schedule and the Settings night mode — can now be limited to specific weekdays (Mon–Fri "night" plan, weekend-only throttle, …). The schedule editors in the plan popover and Settings gain a row of day toggles (none selected = every day), saved plans and prefs carry the days array, and the armed plan's weekday selector comes back across a relaunch.
  • The night pill is a one-click override. Clicking the tray header's night pill forces night mode on or off for this session — no Settings round-trip. The override is session-scoped (never persisted), so the configured clock window applies again on the next launch; the pill shows its state (auto / off (session) / ON (override)).
  • Chip tooltips explain the effective speed. When a plan window or the night cap is what actually binds a transfer, hovering its chip shows the full breakdown — own limit vs plan window (named) vs night cap — and the effective rate with the binding source, so a throttled download is never mysterious.
  • Verified end-to-end. New two-boot scenario: an armed schedule-only plan carries a weekday selector into boot #2 (night-mode weekdays persist too) while the ~40 KB/s window keeps pacing the restored queue; the playtest clicks the pill (off → on), checks a running chip's tooltip names the binding night cap, and saves weekday-restricted plan + night-mode windows (90 pure-Node checks, 8 Electron IPC, 9 two-boot, 65 playtest steps).

v1.4.6 — Per-plan schedules, plan switcher on chips & header

2026-09-05

  • Active-window schedules on queue plans. A plan can now carry a window rule — e.g. a "night" plan capping the whole queue at 100 KB/s between 23:00 and 07:00. The save area gains a window editor (from / to times + a whole-queue cap stepper); while the local clock is inside the window every transfer is throttled live, a transfer's own lower limit still wins, and the tray chips say the cap is a plan window rather than pretending the file chose that speed. A plan may be schedule-only (zero entries).
  • The applied plan leaves the popover. Applying a plan arms it app-wide: its name rides a small badge on every tray chip (with a live "window cap … now" hint when throttling), and a plan switcher in the tray header applies any saved plan — or clears the applied one — in one click, no popover needed. Deleting the applied plan disarms it.
  • Verified in the real window. The playtest saves a schedule plan from the popover editor, applies it, checks the chip badge, then switches and clears it from the tray header; unit tests pin the window math (overnight wrap, end-exclusive, whole-day), the armed whole-queue cap, and the ETA-basis flip (89 pure-Node checks, 8 Electron IPC, 8 two-boot, 59 playtest steps).

v1.4.5 — Folder-batched what-if, named queue plans

2026-09-05

  • Folder-level what-if steppers. In the popover's What-if mode, queued files that share a destination folder are grouped under a folder header with its own limit stepper — cycling it re-ranks the entire same-folder batch at once (files stay grouped when their ETAs tie, exactly like Apply will order them). Per-file steppers remain for fine control.
  • Named queue plans. The applied what-if patch can be saved as a named plan — persisted keyed by destination path (transfer ids are transient across restarts), so a plan is recalled and re-applied whenever the same files are queued again, from the popover's Queue plans list. A folder stepper saves a folder rule that pins every file headed to that folder — including files queued into it later — with genuine per-file deviations kept as overrides that win on apply. A saved plan can also be deleted on demand, and the two-boot suite proves a plan (folder rule + override) survives a relaunch and lands its limits on the restored queue.
  • Deletions now actually persist. This surfaced a real storage bug: updatePrefs merges nested objects, silently resurrecting deleted keys inside collections — a new replacePrefs replaces the whole key so removals stick across reloads (pinned by a unit test).
  • Verified in the real window. The playtest drives the folder stepper (both files re-ranked at once), saves the applied patch as a plan, re-applies it after the limits are changed, and deletes it; the two-boot suite now also proves a saved plan survives a relaunch and re-applies to the restored queue (54 steps; 88 pure-Node checks, 8 Electron IPC, 8 two-boot).

v1.4.4 — Visible smart-order math: byte sizes, ETA bars

2026-09-05

  • The scheduler's math is now on every chip. Under Smart order, each queued file shows the remaining/total byte size alongside its ETA and the speed basis behind it (limit / measured / live network / assumed) — and each active download shows its live ETA next to the progress bar, pacing toward the finish with the same basis. You can see exactly why the queue ranks the way it does.
  • Whole-queue decision popover. An info button next to the Smart order toggle opens a breakdown of the entire start order: every queued file with its ETA, bytes left, rate basis, and a bar scaled to its estimated wait (the slowest file fills the bar), so equal-ETA folder batching and fastest-finishing-first ordering are visible at a glance.
  • What-if preview. Inside the popover, a What if… mode adds a limit stepper to every queued file: cycling a hypothetical limit re-ranks the start order and ETA bars live — nothing is touched until Apply limits commits the patch for real (Reset clears it). The preview is computed by the same ranker as the live queue, so what you see is exactly what Apply produces.
  • Verified in the real window. The playtest asserts the byte text and active-chip live ETA, drives the popover open, checks its per-file rows + ETA bars, re-ranks a hypothetical limit and applies it (50 steps); the pure-Node suite covers the what-if ranker's no-mutation guarantee (85 checks) and the two-boot suite keeps proving smart order + learned speeds survive a relaunch (7 checks).

v1.4.3 — Smart queue ordering, period-filtered tallies, learned speeds

2026-09-05

  • Bandwidth-aware queue scheduling. A Smart order toggle in the tray header switches the start queue from FIFO to estimated-finish ordering — remaining bytes ÷ rate — so the file that will finish first starts first. The queue learns true per-file speeds: each transfer's own measured bandwidth is tracked (smoothed, never polluted by app-imposed limits), re-ranks the queue live as streams progress, and is persisted with the resume record so a restored queue is ordered by the speeds actually observed last session. Equal-ETA files batch by destination folder, so same-folder batches start together instead of interleaving by arrival.
  • Per-period tallies. The Downloads-by-source panel on the Library views gained an All time / This week / This month selector (each source keeps bounded timestamped events), plus a Copy CSV button that exports the selected period's table to the clipboard for pasting into a spreadsheet.
  • Verified across real boots. The two-boot suite now also proves per-transfer speed limits and a drag-reordered queue survive a relaunch (6 checks), and the pure-Node suite grew to 83 checks.

v1.4.2 — Drag-and-drop queue, lifetime download tallies, pause survives restart

2026-09-05

  • Drag-and-drop queue reordering. Queued tray chips are draggable — grab one and drop it onto a sibling to splice it into that queue slot (the old up/down arrows remain for fine moves). Backed by a new absolute-position moveTo IPC, so the dragged chip lands exactly where you put it.
  • Lifetime per-source download tallies. The Favorites and Recent views open with a Downloads by source panel: files + bytes per source (Internet Archive, distro ISOs, Arch, Demo, other), sorted by volume with a proportional bar and a lifetime total. Counts are persisted and survive restarts — clearing the tray never clears the tallies.
  • A user pause survives a restart. Paused transfers are now persisted as paused: relaunch parks them (partial kept, zero network activity) instead of dropping them — resume stays manual, exactly as the user left it. The two-boot test now proves both directions: interrupted downloads auto-resume, paused ones stay parked, and per-source folder rules ride through a relaunch.

v1.4.1 — Pause, per-source folders, real-app CI

2026-09-05

  • Pause instead of cancel. A running transfer now has a dedicated pause button: the stream stops, the .part is kept, and the queue slot frees up for the next file — the tray parks it as Paused with a one-click resume (Range-continues from the partial). Removing a paused transfer explicitly deletes its partial.
  • Per-source default folders. Settings → Library lets you choose a default save folder per direct-file source (Internet Archive, Ubuntu/Debian, Arch, Demo) — Archive items land in your Archive folder, ISOs in your ISO folder — falling back to the shared last-used folder when unset. The chosen folder is remembered per source at save time.
  • Real-app CI. The ci workflow now also runs the Electron IPC suite and the two-boot auto-resume test (a genuine download quit mid-flight, then verified resumed after relaunch) on Windows runners with every push, so restart-resume regressions can’t ride a release tag.

v1.4.0 — Direct downloads, resumable

2026-09-05

  • Download the file, not just the magnet. Internet Archive items open an in-app file picker and stream the chosen file straight to disk through your VPN/proxy route (host allowlist re-validated on every redirect). Official Ubuntu/Arch ISOs download directly from the mirror. Torrent-only sources still hand off to your torrent client.
  • Resume + a bounded queue. At most two transfers stream at once — the rest queue FIFO in the downloads tray, queued rows get up/down arrow buttons to reorder what starts next. An interrupted download keeps its .part; retrying continues with an HTTP Range request instead of restarting. The save dialog remembers your last folder, and finished transfers reveal in the OS file manager (button or right-click).
  • Per-download speed limit. Each running transfer shows a small limit control (unlimited → 100 KB/s → 256 KB/s → 512 KB/s → 1 MB/s); it applies live, mid-stream. Bytes stream through a token bucket on the same proxy-aware path as search. Settings → Library also sets a default limit for every new download.
  • Survives restarts. In-flight downloads are persisted; next launch re-queues them automatically and continues from the .part — an interrupted file picks up where it stopped, no dialog needed. Verified end-to-end by a dedicated two-boot test that quits the real app mid-download and asserts the relaunch resumes it.
  • Demo cards are fully downloadable offline — their download button opens the picker over locally-generated, clearly-labeled sample files, so picker → save → progress → done is testable with zero network (the real-window playtest now drives it).
  • Animated launch intro — the splash ring/magnet draw now plays for a minimum showcase time before the main window appears.
